# Vercel's AI Library Patches Critical Serialization Vulnerability in Tool Approval System

Vercel has released version 7.0.36 of its popular AI library, addressing a significant security flaw in how tool approval signatures are generated and verified. The patch fixes a cryptographic vulnerability in the `experimental_toolApprovalSecret` feature that could have allowed attackers to forge valid signatures for unintended tool calls by exploiting an ambiguous serialization format.

## TL;DR

- **Serialization vulnerability**: The tool approval system used newline-delimited fields to create HMAC signatures, but fields containing newlines could create identical byte sequences from different inputs
- **Attack vector**: Malicious actors could craft signatures that verify against multiple different tool calls, bypassing intended approval controls
- **The fix**: The library now uses `JSON.stringify()` with a versioned prefix for unambiguous encoding, while maintaining backward compatibility with old signatures where possible
- **Impact**: Projects using tool approval authentication should update immediately to close the signature collision vulnerability

## Background

The Vercel AI library provides developers with tools to integrate large language models into applications. One of its experimental features, `experimental_toolApprovalSecret`, allows applications to cryptographically sign and verify tool calls before execution—essentially creating an approval gate where only authorized function invocations can proceed.

This feature is particularly important in scenarios where an LLM has access to powerful functions (like database writes or API calls) and developers want to ensure that only legitimate tool invocations, signed with a specific secret, are actually executed. The signature mechanism acts as a second layer of validation beyond simple access control.

However, the original implementation had a subtle but serious flaw in how it serialized the data being signed. By using newline characters as delimiters between fields, the system created an opportunity for what's known as a "collision" attack—where two different sets of data could produce identical signatures.

## How it works

### The Original Problem: Delimiter Ambiguity

The vulnerability centered on how the HMAC payload was constructed. The original code took fields like `toolName`, `toolCallId`, and other parameters and simply joined them with newline (`\n`) separators:

```
toolName\ntoolCallId\nother_data
```

This approach seems straightforward until you consider that field values themselves can contain newline characters. Imagine a tool named `"execute\nmalicious"` and another tool named `"execute"` followed by `"malicious"`. Without proper escaping, these could serialize identically, creating an ambiguous encoding.

The cryptographic consequence is severe: an attacker with knowledge of the signing process could potentially create a valid signature for tool call A, then later use that same signature to authorize a completely different tool call B if the fields were arranged to create identical serialization.

This is known as an "injective" encoding problem—the original format was not injective, meaning multiple distinct inputs could map to the same output. Cryptographic protocols require injective encodings to prevent exactly this kind of forgery.

### The Solution: JSON Serialization with Domain Separation

Vercel's patch implements a more robust serialization approach using `JSON.stringify()` with a versioned domain-separation prefix. This approach has several advantages:

**Character escaping**: JSON.stringify() automatically escapes special characters including newlines, quotes, and control characters. A newline within a field becomes the literal characters `\n` in the JSON output, not an actual line break. This means two different field combinations cannot accidentally serialize to identical bytes.

**Versioning**: By adding a versioned prefix to the domain-separated payload, the library builds in forward compatibility. If the serialization format needs to change again in the future, the version prefix ensures old and new signatures won't be confused.

**Injectivity guarantee**: The combination of JSON encoding rules and domain-separation ensures that the function mapping inputs to serialized bytes is now injective—each unique set of fields produces a unique byte sequence.

### Backward Compatibility Preservation

Rather than immediately invalidating all existing signatures, Vercel implemented a thoughtful compatibility layer. When verifying signatures, the library still accepts the old format—but only in cases where no collision is actually possible. Specifically, old-format signatures only verify successfully when fields don't contain the newline delimiter, which was the exact condition that made the old format dangerous.

This approach prevents immediate breakage for applications mid-upgrade: an approval signature generated before the update will still work as long as it doesn't hit the edge case that exposed the vulnerability. However, the collision vulnerability is definitively closed because the new format always uses the safer JSON serialization.

## What happens next

For developers using the Vercel AI library, the recommendation is straightforward: update to version 7.0.36 or later. The patch requires no code changes for most users—it's transparently applied during signature verification. Applications that haven't yet issued tool approval signatures with the old format won't be affected at all.

For teams relying heavily on `experimental_toolApprovalSecret` in production environments, this update should be prioritized in your deployment pipeline. The vulnerability window closes once both signature generation and verification use the new format, which happens automatically after updating.

This fix exemplifies why cryptographic implementations require careful attention to encoding details. Even seemingly minor serialization choices can have serious security implications when they're part of a signature mechanism.
