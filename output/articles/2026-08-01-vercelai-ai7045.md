# Vercel AI SDK 7.0.45: Expanded Tool Calling and Streaming Improvements

Vercel has released version 7.0.45 of its popular AI SDK, introducing experimental support for tool callers in streaming contexts and adding new safeguards for streaming configuration. This patch update addresses workflows where language models need to execute tools in real-time streaming scenarios, a capability that becomes increasingly important as developers build more complex agentic applications.

## TL;DR

- **Experimental Tool Callers**: The SDK now supports `experimental_toolCallers` in `streamText`, enabling tools to be called during streaming text generation
- **ToolLoopAgent Enhancement**: Tool calling capabilities have been extended to the `ToolLoopAgent` class for more flexible agent patterns
- **Streaming Configuration Validation**: New warnings prevent misconfiguration when incompatible streaming-only settings are passed to non-streaming functions
- **Impact**: Developers building AI agents with tool use can now leverage streaming responses more effectively, improving perceived latency and user experience

## Background

Tool calling—the ability for language models to request execution of external functions—has become a fundamental pattern in modern AI applications. Models like GPT-4, Claude, and others can analyze user requests and determine which tools to invoke, creating a loop where AI systems can interact with APIs, databases, and custom logic.

However, streaming responses and tool calling have historically existed in separate worlds. Streaming allows responses to arrive token-by-token, providing users with immediate feedback as the model generates text. Tool calling traditionally required waiting for the complete model response before parsing tool invocations.

This patch bridges that gap. The addition of experimental tool caller support in streaming contexts means developers no longer need to choose between responsive streaming interfaces and the capability to invoke tools mid-response.

## How it works

### Streaming Text with Tool Callers

The introduction of `experimental_toolCallers` in the `streamText` function represents a significant architectural shift. Previously, developers using the AI SDK had to select between two paradigms: either stream the raw text generation without tool execution, or await the complete response before processing tool calls.

With this update, tool calls can be triggered during the streaming process itself. This is particularly valuable for scenarios where a model might generate some text, invoke a tool to fetch information, and then continue generating based on that result—all while streaming tokens to the user. The implementation is marked as experimental, indicating the API may evolve based on developer feedback and usage patterns.

The practical benefit is substantial: imagine a customer service chatbot that receives a question about an order. Instead of waiting for the full response to be generated, parsed, and processed, the system can now call the order lookup tool as soon as the model decides it needs that information, with results flowing back into the context for continued generation.

### ToolLoopAgent Expansion

The `ToolLoopAgent` class has similarly received experimental tool caller support. This agent pattern represents a more structured approach to building AI systems that need to perform multiple operations in sequence. By extending tool caller capabilities to this agent type, developers gain additional flexibility in how they structure their agentic loops.

The ToolLoopAgent is useful for scenarios requiring orchestration—situations where an AI needs to call multiple tools, evaluate results, and decide on next steps iteratively. Adding streaming-compatible tool calling means these agents can now operate in more responsive environments without sacrificing the structured control that the agent pattern provides.

### Streaming Configuration Warnings

A subtle but important addition in this release addresses a common configuration error: the `generateText` function now warns developers when they provide streaming-only configuration options like `firstChunkMs` or `chunkMs`. These timeout settings are designed specifically for streaming scenarios, where the system needs to monitor how long it takes to receive the first chunk or subsequent chunks from the model.

When applied to `generateText`—which returns a complete response rather than streaming tokens—these settings become meaningless and can indicate a developer misunderstanding the API contract. The new warning surfaces this issue immediately during development rather than silently ignoring the configuration.
