# Vercel AI SDK 7.0.19: Securing Tool Definitions Against "Rug Pull" Attacks

Model Context Protocol (MCP) tools have become essential for extending AI capabilities, but a new version of Vercel's popular AI SDK addresses a critical security concern: attackers modifying tool definitions after initial trust. This patch release introduces mechanisms to detect and prevent what the team calls "rug pulls"—malicious changes to tool specifications that could trick language models into executing unintended actions.

## TL;DR

- **Tool fingerprinting**: Lock down tool definitions at the moment of trust, creating a baseline for later verification
- **Drift detection**: Compare subsequent tool fetches against the baseline to identify unauthorized modifications
- **Property safety**: Fix edge cases where tool names could collide with JavaScript object properties
- **Impact**: Teams using MCP tools gain stronger guarantees that tool behaviors haven't been silently modified between trust decisions and execution

## Background

MCP tools allow AI models to interact with external systems—databases, APIs, file systems. When a developer approves a tool, they're trusting both the tool's current definition and the system that hosts it. But what happens if that host is compromised? What if someone modifies a tool's description or expands its input schema after approval?

This vulnerability has real consequences. A tool initially designed to "list files in a directory" could be modified to "delete files" without the approving party's knowledge. The AI model would execute the modified version, believing it's performing the originally-approved action. This is the "rug pull"—a bait-and-switch where trust is established then exploited.

Previous versions of the SDK offered no mechanism to detect such changes. Once a tool was approved, the system trusted every subsequent fetch from the MCP server without question.

## How It Works

### Fingerprinting Tools at Trust Time

The new `fingerprintTools` function creates a cryptographic or deterministic snapshot of critical tool properties when approval is granted. Rather than storing the entire tool object—which could be voluminous—the SDK records immutable fields: the tool's string description, JSON input schema, and title.

Think of this as taking a photograph of the tool at a specific moment and keeping that photo for comparison. The fingerprint captures what the developer or security team explicitly approved. This baseline becomes the source of truth against which future versions are compared.

The responsibility for storing these fingerprints remains with the application. This design keeps the SDK lightweight and flexible, letting teams integrate fingerprint storage into their existing approval workflows, policy databases, or audit logs.

### Detecting Drift After Fetch

When MCP tools are fetched later—potentially hours or days after the initial approval—the `detectToolDrift` function compares the current tool definition against the stored fingerprint. If the description has changed, if the input schema has expanded to accept new parameters, or if the title differs, the drift detector flags the discrepancy.

This creates an opportunity to halt execution before passing potentially-modified tools to the language model. An application might log the drift, alert administrators, revoke approval, or trigger manual review. The SDK detects the problem; the application decides the response.

This two-phase approach—fingerprint then verify—mirrors security practices in container image verification, code signing, and software supply chain protection.

### Fixing Property Name Collisions

A subtler but important fix addresses a JavaScript quirk. In JavaScript, objects inherit properties like `constructor`, `toString`, `valueOf`, and `__proto__` from their prototype chain. If someone names a tool `"constructor"` or `"toString"`, checking for tool-specific approvals could accidentally access inherited properties instead of the actual tool approval configuration.

The patch uses own-property checks—explicit verification that a property belongs to the object itself, not its prototype—when resolving per-tool approvals. This prevents a tool named `"constructor"` from accidentally retrieving a prototype method's configuration. The `@ai-sdk/policy-opa` module now builds its per-tool approval map with a null prototype to eliminate inheritance entirely, adding an extra layer of safety.

This fix may seem esoteric, but it prevents subtle security bypasses where carefully-named tools could obscure their approval status.

### Preserving Signatures Through State Transitions

When tool approvals transition from awaiting response to having received one, signature data that validates the approval itself is now preserved. This maintains the cryptographic chain of custody, ensuring that approval records remain verifiable even as their status changes.

## What Happens Next

The security model here acknowledges a reality: the SDK can detect problems but can't solve them unilaterally. It detects tool drift and property collisions, but enforcement depends on application logic. This is by design—different teams have different trust models, different tolerance for tool changes, and different remediation strategies.

Teams using MCP tools should consider integrating fingerprinting into approval workflows. When a tool is explicitly approved, capture its fingerprint immediately. Before passing tools to models, verify against those fingerprints. This transforms tool approval from a one-time binary decision into an ongoing verification process.

For teams already using the policy-OPA module or other approval frameworks, the property-name fixes ensure that approval checks remain robust across unusual edge cases.

This release reflects a maturing understanding of AI safety: security isn't just about preventing the model from misbehaving, but about maintaining trust in the tools it uses and detecting when that trust has been violated.
