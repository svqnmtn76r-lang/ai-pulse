## Background

Generating structured data from language models presents a persistent challenge. While modern AI models excel at understanding and processing natural language, extracting reliable, properly-formatted objects—such as JSON structures with specific schemas—requires additional techniques. Models occasionally produce malformed output, incomplete responses, or text that doesn't strictly adhere to requested formats.

The `repairText` feature was initially introduced as an experimental tool to address this problem. It provides a mechanism to automatically correct and normalize text output from models when generating structured objects. By marking it experimental, Vercel's team could gather real-world usage data, identify edge cases, and refine the implementation before committing to long-term API stability.

Over several releases, developers have tested and deployed applications using this experimental feature. Sufficient evidence of reliability and utility has accumulated to justify promoting it to stable status, which means Vercel is committing to maintaining API compatibility for this feature in future releases.

## How it works

### Text Repair for Structured Generation

When using the AI SDK's `generateObject` or `streamObject` functions, developers define a schema that specifies the expected structure of the returned data. Language models generate text responses that should conform to this schema, but occasional formatting errors or partial responses can occur, particularly with larger or more complex schemas.

The `repairText` option enables automatic correction of these responses. Rather than returning malformed data or throwing errors when output doesn't match expectations, the system attempts to repair the text into valid, schema-compliant output. This improves reliability when working with less capable models or when dealing with edge cases where even sophisticated models might stumble.

The feature works at the generation layer, intercepting model output before returning it to the application. This transparent approach means developers don't need to implement custom retry logic or validation workarounds—the repair mechanism handles common issues automatically.

Applications currently using `experimental_repairText` will continue functioning without modification, but developers receive signals—typically through TypeScript warnings or documentation—that they should migrate to the new name.

This approach balances the needs of stability and progress. Users can upgrade to version 7.0.39 without immediate pressure, then update their code at their own pace.
